# Plan: model-comparison-harness

**Script first, operator flow second, documents last.** Everything the harness decides mechanically — settings validation, selection, the estimate and its approval token, the isolated checkouts, the replay's step sequence, the routing check, the outcome, the blinded ranking and the report — is one new script, `scripts/compare.sh`, pinned by one new sweep, `scripts/test-compare.sh`. The sweep drives every agent step through a stub named by `ORCH_COMPARE_CLAUDE`, so, like `test-metrics.sh`, it needs no live agent. The skill that talks to the operator (T17) lands after every subcommand it names. A prompt that names a subcommand the script does not have yet would make the operator's session improvise a replay, and an improvised replay is one that dispatches from the main checkout and fails its own routing check. T1–T15 all edit `scripts/compare.sh` and `scripts/test-compare.sh`, so they run in sequence. Only T16 (script) and T17 (skill) fan out after T15. T20 (the Opus 5.5 price entry) and T19 (fixed effort, which refuses an unpriced pinned model and so needs T20's entry) were filed after T1–T10 landed; their IDs are frozen, so they sit before T11 by position and T11 depends on them.

**The harness changes nothing the live loop runs.** No task edits `runstate.sh`, `routing.sh`, `metrics.sh`, `spend.sh`, a hook, or an agent prompt, except T20's price entry, which `session-effort-reporting` assigns here. Replays call those as they stand: the PRD puts changing how the loop reviews, routes or lands out of scope. A field the harness needs that one of them does not produce is a finding for the owning feature, not a local patch. The plan assumes `implementer-continuation` (`continue`, `refresh-handoff`) and `dispatch-progress-metrics` (per-dispatch rows) have landed, as the roadmap's `depends_on` orders.

**Four decisions, made here because the decomposition needs them.**
1. **Isolation is a clone, not a worktree.** `routing.sh`, `runstate.sh`, the pause sentinel and `hooks/metrics-log.sh` all find their config root through `git rev-parse --git-common-dir`. From a worktree that is the main checkout, so a worktree replay would read and write the main checkout's `.agents/` and its routing config. That breaks both the isolation criterion and "set through `model_routing` in the replay's configuration". A `git clone --shared` at the parent commit resolves to itself. It lives in an opaque-named directory under `${ORCH_COMPARE_SCRATCH:-$TMPDIR}`, outside the main checkout, on an opaque clone-local branch. So the main checkout's tree, `.agents/` and refs are untouched by construction. This is self-contained work off the default branch, the case CLAUDE.md reserves isolation for, and never a loop packet.
2. **The harness is its own driver, and each agent step is a headless session whose working directory is the clone.** An agent dispatched from the operator's session is stamped by the metrics hook with the main checkout's routing, so the replay's model would count as an override. The reviewer also cannot run in the checkout whose `.agents/project-overrides.yaml` names the subject model. So `compare.sh replay` walks the `run-loop` §3 sequence itself, using the loop's own `runstate.sh` subcommands (`handoff`, `check-status`, `route`, `refresh-handoff`, `write-result`) in that section's order. Each varied-role step is a non-interactive, time-limited session in the work clone, which dispatches the agent with `routing.sh resolve` exactly as the loop does. Each review runs the same way in a separate blinded review view (T6). The escalation decider is never dispatched. **Every script, hook and agent definition a replay, review view or ranking session uses comes from the harness repository's current checkout, never the clone's:** each session is launched with `--plugin-dir <harness checkout>`, and scripts are invoked by that path with `--root <clone>`. The clone supplies only the working tree and `.agents/` configuration — because in this repository the clone at a parent commit carries older copies of `agents/`, `hooks/` and `scripts/` (or none), and the committed `.claude/settings.json` disables the plugin, so an unpinned session would run the old loop or no loop at all.
3. **The estimate (PRD deferred decision 1) holds tokens constant and prices them per model.** Each packet's forecast is its original recorded token breakdown — `packets[].tokens` from the source repository's stored `run-metrics.json` — priced at each model's rates in `scripts/spend-prices.json`, stamped with that table's date. Fix rounds are not modelled. The original cost already includes the original run's rounds, and forecasting different rounds per model would assume the answer the experiment exists to measure.
4. **Results live in `.agents/metrics/comparisons/` in the harness repository's main checkout (PRD deferred decision 2).** It sits outside `.agents/loop/`, so `begin-run`'s pruning never reaches it. It is already gitignored as bookkeeping in both `.gitignore` files, as all of `.agents/metrics/` is. Records are append-only JSONL, and each record embeds the settings that produced it. The label-to-model map is a separate file from anything a ranking session receives. An experiment's id is a digest of its normalized settings, so identical settings resume and changed settings start a new experiment beside the old one.

**The proposal is computed, not written by a model.** P1 requires two renders of the same stored results to match byte for byte, and only a deterministic rule does that. The proposed value is the model with the highest pass rate across both classes, then the lowest mean rank, then the lowest mean dollar cost. A class "favours" a model by the same rule applied inside that class.
